# data-processors Specification

## Purpose
Массовые операции над учётными данными: формирование запросов поставщикам по отобранным заявкам, пересчёт таймингов маршрутов, выявление просроченных сроков и SLA, сводка статусов, а также контракт вычисления сальдо и KPI по движениям регистров.

## Requirements

### Requirement: Обработка формирует запросы поставщикам по отобранным заявкам

Система SHALL по отобранным пользователем заявкам в статусе `ВРаботе` создавать заказы поставщику по услугам, для которых заказ ещё не создан, и SHALL выводить результат по каждой заявке: создано, пропущено с причиной, ошибка. Повторный запуск SHALL не создавать дублей.

#### Scenario: Массовое формирование по пяти заявкам

- **WHEN** отобраны пять заявок без заказов поставщику
- **THEN** создаются заказы по всем требуемым услугам, а результат содержит пять строк со статусом «создано»

#### Scenario: Повторный запуск

- **WHEN** обработка запущена повторно по тем же заявкам
- **THEN** новые заказы не создаются, каждая заявка помечается как пропущенная с причиной «заказ уже существует»

#### Scenario: Заявка без услуг

- **WHEN** в заявке нет требуемых услуг
- **THEN** заявка попадает в результат как пропущенная с указанием причины, остальные заявки обрабатываются

### Requirement: Обработка пересчитывает тайминги маршрутных листов

Система SHALL пересчитывать локальное время событий и буферы между ними для выбранных маршрутных листов и SHALL выводить список выявленных накладок. Проведённые документы SHALL изменяться только при явно установленном флаге пересчёта проведённых.

#### Scenario: Пересчёт трёх маршрутов

- **WHEN** выбраны три маршрутных листа и флаг изменения проведённых не установлен
- **THEN** непроведённые листы пересчитаны, проведённые пропущены, в результате указано количество пересчитанных и пропущенных

#### Scenario: Обнаружена накладка

- **WHEN** после пересчёта буфер между соседними событиями отрицателен
- **THEN** событие попадает в список накладок с указанием маршрута, события и величины перекрытия

### Requirement: Обработка выявляет просроченные сроки и SLA

Система SHALL выявлять услуги с истёкшим контрольным сроком без подтверждения и запросы с истёкшим `СрокSLA` без исполнения и SHALL по требованию пользователя формировать задачи эскалации ответственным.

#### Scenario: Есть просрочки

- **WHEN** на текущую дату две услуги без подтверждения просрочены и один запрос просрочен по SLA
- **THEN** результат содержит три строки с видом просрочки, объектом и ответственным, а при включённом флаге создаются три задачи эскалации

#### Scenario: Просрочек нет

- **WHEN** все контрольные сроки и сроки SLA не истекли
- **THEN** результат пуст, задачи не создаются, сообщение об ошибке не выводится

### Requirement: Обработка формирует сводку статусов за период

Система SHALL формировать сводку статусов заявок, подтверждений, инцидентов и претензий за выбранный период с группировкой по статусу и объекту и SHALL позволять выгрузить результат в файл.

#### Scenario: Сводка за квартал

- **WHEN** выбран период квартала, за который есть заявки, подтверждения, инциденты и претензии
- **THEN** сводка содержит количество по каждому статусу каждой сущности, а выгрузка сохраняет те же значения

#### Scenario: Пустой период

- **WHEN** за выбранный период документов нет
- **THEN** сводка формируется пустой, без сообщений об ошибке, выгрузка содержит только заголовки

### Requirement: Сальдо по претензии вычисляется по движениям регистра

Система SHALL вычислять сальдо по претензии как разницу между суммой требования и суммой удовлетворения, накопленными в регистре `ВзаиморасчётыПоПретензиям`, а не по реквизитам документов.

#### Scenario: Частичное удовлетворение

- **WHEN** по претензии заявлено требование 100 000 и проведён акт на 60 000
- **THEN** сальдо по претензии равно 40 000

#### Scenario: Претензия без акта

- **WHEN** по претензии есть требование, но нет удовлетворения
- **THEN** сальдо равно сумме требования

### Requirement: KPI сотрудника считается по движениям регистра

Система SHALL вычислять KPI сотрудника как количество операций и суммарное время обработки по каждому виду операции из регистра `KPIОператоров`.

#### Scenario: KPI по подтверждениям

- **WHEN** сотрудник провёл три подтверждения услуг
- **THEN** по виду операции «ОбработанаЗаявка» количество равно трём, а время обработки равно сумме значений регистра по этим записям

#### Scenario: Операций нет

- **WHEN** у сотрудника за период нет движений
- **THEN** KPI равен нулю по количеству и времени, сотрудник выводится со значением «нет операций»

### Requirement: Аналитические обработки не изменяют учётные данные

Система SHALL выполнять сводку статусов, расчёт сальдо и расчёт KPI без записи документов и движений: такие обработки работают только на чтение.

#### Scenario: Запуск сводки не меняет регистры

- **WHEN** сводка статусов сформирована
- **THEN** количество записей регистров и документов до и после запуска совпадает

### Requirement: Массовые операции подчиняются правам доступа

Система SHALL разрешать массовые операции только профилям, имеющим право на изменение соответствующих документов, и SHALL сообщать об отказе, не раскрывая состав данных.

#### Scenario: Запуск без прав

- **WHEN** пользователь без права изменения заказов запускает массовое формирование запросов
- **THEN** обработка не выполняется, выводится сообщение об отсутствии прав, документы не создаются
