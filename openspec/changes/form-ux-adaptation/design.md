# Design

## Context

См. `proposal.md` — Why. Что важно для реализации:

- 34 формы этапа 3 собраны пресетом `form-compile -FromObject` и уже являются основными в метаданных. В них есть `ГруппаШапка`, `ГруппаПараметры`, `ГруппаДополнительныеРеквизиты`, `ГруппаСтраницы`, табличные части и пустые `РасширеннаяПодсказка`.
- В формах нет ни одного `<Commands>`, ни одного `<ConditionalAppearance>`, нет `AutoMarkIncomplete`; все `Ext/Form/Module.bsl` пустые.
- В подсистемах нет `<CommandInterface>`; состав объектов зафиксирован в `docs/Отчёт-по-подсистемам.md`.
- Ограничения проекта: файловая ИБ `db\КурсоваяРабота`; лицензия на одно место (перед загрузкой закрывать сеансы); правка `Form.xml` скриптом с сохранением одного BOM и табов — двойной BOM ломает XML; `form-compile -FromObject` не переносит готовые элементы, поэтому доработка — только точечная правка существующих форм.
- `form-add`/`form-compile`/`form-validate`/`form-info` и `interface-edit` доступны как скиллы, `form-validate` — обязательный шаг после каждой правки.

## Goals / Non-Goals

**Goals:**

- Единый визуальный контракт карточек и журналов: шапка → основное → «Дополнительно» → подвал.
- Проблемные значения видны без открытия карточки: просрочка, расхождения, тяжёлые инциденты, превышение порога, отрицательные значения.
- Типовые операции доступны с формы и из панели навигации раздела.

**Non-Goals:**

- Проведение, движения регистров, расчёты компенсаций и SLA — этап 4.
- Отчёты, обработки, мобильный клиент, веб-публикация — этап 5.
- Изменение состава метаданных, типов реквизитов и синонимов (включая найденные опечатки `Договоры споставщиками`, `Акт окомпенсации`, `Slaчасов`, `Emailресепшн` — отдельная задача).
- Формы регистров и подсветка отрицательных остатков по РН `ГрафикПеремещений`: остатков нет до этапа 4. Вместо них реализуются отрицательный буфер события и неположительные количества/суммы в ТЧ (см. `specs/object-forms`).
- Изменение состава ролей и профилей — отдельный остаток этапа 3.

## Decisions

### D1. Правим существующие формы, а не создаём новые

Все 34 формы уже основные; ссылки на них есть в подсистемах и в смоук-тестах. Новые формы пришлось бы назначать основными, а старые удалять — это ломает смоук и историю.

Альтернатива: пересобрать формы `form-compile -FromObject` с новыми пресетами. Отклонено: пресет не умеет условное оформление, команды и подсказки, а ручные правки после пересборки всё равно нужны.

### D2. Волновая правка с валидацией после каждой волны

1. Карточки: раскладка, скрытие, обязательные, подсказки (23 формы).
2. Журналы: условное оформление по срокам, статусам, расхождениям (11 форм).
3. Карточки: условное оформление по порогу и отрицательным значениям.
4. Команды форм и модули (навигация, основание, сервисные, заготовки).
5. Командный интерфейс подсистем.

Волна закрывается `form-validate` по всем затронутым формам + загрузкой в ИБ + xdd-смоуком. Так ошибка XML не размазывается на 34 формы.

### D3. Условное оформление задаётся декларативно на форме

Используется `ConditionalAppearance` формы: элементы условий — поля основной таблицы (журнал) или `Объект.<Реквизит>` (карточка), оформление — `ЦветФона`/`ЦветТекста` через `Формат`.

Палитра фиксирована, чтобы журналы читались одинаково:

| Смысл | Фон | Текст |
|---|---|---|
| Ошибка: просрочка, тяжёлый инцидент, отклонённая претензия, отрицательное значение | `#FFC7CE` | `#9C0006` |
| Предупреждение: расхождение, ожидание ответа | `#FFEB9C` | `#9C6500` |
| Успех: оплачено, согласовано | `#C6EFCE` | `#006100` |

Альтернатива: раскрашивать через `ПриВыводеСтроки`/`ПриПолученииДанных`. Отклонено: это код в модуле формы, лишние запросы и сложность сопровождения; декларативные правила платформа считает сама.

### D4. Порог согласования передаётся реквизитом формы

У `ПретензияПоставщику` (карточка и журнал) добавляется реквизит формы `ПорогСогласования` (Число 15,2), который заполняется в `ПриСозданииНаСервере` из константы `ПорогСогласованияРуководителем`. Условие подсветки: `СуммаТребования > ПорогСогласования И НЕ СогласованоРуководителем`.

Альтернатива: тянуть константу в запрос динамического списка журнала. Отклонено: динамический список журнала сгенерирован автоматически, вмешательство в запрос усложняет форму и тесты ради одного числа.

Важно: у константы нет значения по умолчанию, фактически это 0. При пороге 0 правило не подсвечивает ничего — это записывается в подсказку поля и проверяется в тесте после установки порога.

### D5. Команды живут в форме, модули форм перестают быть пустыми

Команды объявляются в `<Commands>` формы, обработчики — в `Ext/Form/Module.bsl`. Это осознанный отход от конвенции этапа 3 «модули форм пустые»: без обработчиков команды не работают. Привилегированный режим не используется, права проверяются явно через `ПравоДоступа`.

Альтернатива: общий модуль команд. Отклонено: общий модуль пришлось бы создавать с нуля (их в конфигурации нет), а команды строго привязаны к конкретной форме.

### D6. Создание на основании — параметр формы, а не механизм метаданных

В метаданных документы не связаны как «ввод на основании», и менять состав метаданных вне скоупа. Поэтому:

- команда-источник открывает форму приёмника с параметром `Основание`;
- форма приёмника в `ПриСозданииНаСервере` вызывает `ЗаполнитьПоОснованию(Основание)` и заполняет реквизиты/ТЧ;
- новый документ не записывается до явной команды «Записать».

Связи: `ЗаказПоставщику` → `ПодтверждениеУслуги` (шапка + `ПодтверждённыеУслуги` из `Услуги`), `Инцидент` → `ПретензияПоставщику` (шапка + сумма по договору), `ПретензияПоставщику` → `АктОКомпенсации` (шапка + `СтруктураКомпенсации`).

### D7. Заготовки этапа 4 — честные заглушки

Стандартные команды платформы («Провести», «Записать») уже есть в авто-командной панели документов и не дублируются. Вместо них добавляется по одной предметной заготовке на документ — точки вызова будущих расчётов: «Выполнить сверку», «Пересчитать суммы», «Пересчитать тайминги», «Рассчитать срок SLA», «Рассчитать компенсацию», «Классифицировать», «Применить корректировку», «Пересчитать локальное время», «Пересчитать структуру» (соответствие объектам — в `specs/navigation-and-commands`).

Обработчик выводит `Сообщить("... будет реализовано на этапе 4")`, не пишет объект и не меняет статусы. В коде — маркер `// TODO этап 4`, чтобы при реализации логики команды находились поиском. Заглушки не скрываются: они фиксируют точки расширения и проверяются смоуком.

### D8. Навигация — `CommandInterface` листовых подсистем

Правка выполняется скиллом `interface-edit`. Для каждой из 19 листовых подсистем:

- в панель навигации попадают команды открытия списков/форм своих объектов;
- порядок: сначала «Открыть <журнал>», затем «Создать <объект>», затем остальные формы;
- регистры, бизнес-процессы и задачи, входящие в подсистему служебно, скрываются;
- верхние подсистемы не настраиваются отдельно — они агрегируют листовые.

Состав объектов берётся из `docs/Отчёт-по-подсистемам.md`, отклонений не вводим.

**Отклонение (2026-10-20, согласовано с заказчиком).** Пункт «порядок: сначала «Открыть <журнал>», затем «Создать <объект>»» выполнен частично. Панель навигации подсистемы выводит только команды открытия списков. Стандартную команду создания платформа в неё не помещает: проверены `CommandsPlacement` с `Placement=Auto`, с `Placement=Manual` и без `Placement`; во всех случаях конфигурация загружается, записи сохраняются при выгрузке из базы, но команда в панели не появляется. Создание остаётся штатной кнопкой «Создать» в командной панели формы списка. Обходной путь — 10 общих команд (`CommonCommand`) с группой «Панель навигации.Обычное» — отвергнут как дублирование штатных команд платформы.

### D10. Подсказки — обязательные и неочевидные, текст деловой

Подсказка заполняется для каждого обязательного реквизита и для полей с неочевидной семантикой: `ДатаОжиданияПодтверждения`, `СрокSLA`, `РезультатСверки`, `Источник`, `СогласованоРуководителем`, `БуферДоСледующегоМинут`, `ПроцентШтрафа`, `МаксимальнаяКомпенсация`, `ПорогСогласованияРуководителем`. Тексты — из формулировок раздела 5 Дополнения к ТЗ, без выдумывания новых правил.

## Risks / Trade-offs

- **[Повреждение XML при массовой правке]** → правка через скилл `form-edit`, один BOM, `form-validate` после каждой формы, загрузка волной; откат `git checkout -- <path>`.
- **[34 формы — разъезд конвенций]** → единая палитра и единый чек-лист раскладки в задачах, выборочный `form-info` на 5 формах каждой волны.
- **[Модули форм перестают быть пустыми]** → в модулях только обработчики команд и `ПриСозданииНаСервере`; привилегированный режим запрещён, права проверяются явно, код проходит `1c-lsp-diagnostics`.
- **[Порог согласования = 0]** → правило не подсвечивает; в задаче фиксируется проверка с явно установленным порогом, подсказка поля объясняет смысл.
- **[Заглушки этапа 4 воспринимаются как баг]** → текст сообщения прямо говорит, что логика появится на этапе 4; заглушки перечислены в `docs/Оставшиеся-задачи.md`.
- **[Одно место лицензии]** → перед загрузкой и смоуком закрываются сеансы 1С; загрузка выполняется отдельной задачей волны.
- **[Подсветка в журналах не видна на пустых данных]** → проверка выполняется на демо-данных этапа 3, где есть просроченные даты и расхождения; при отсутствии подходящих строк — создаётся тестовый документ и удаляется после проверки.

## Migration Plan

1. Правки в `src\КурсоваяРабота` волнами, каждая волна — отдельный коммит.
2. Загрузка: закрыть сеансы 1С → `db-load-xml -UpdateDB` для `db\КурсоваяРабота`.
3. Проверка: `form-validate` по формам волны, затем `powershell -ExecutionPolicy Bypass -File tests/vanessa/run-xdd-smoke.ps1`.
4. Откат: `git revert` коммита волны + повторная загрузка XML в ИБ; отдельного скрипта отката не требуется, источник истины — XML.
