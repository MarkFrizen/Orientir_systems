# Spec Delta

## Purpose

Определяет ролевую модель доступа конфигурации: набор ролей-профилей минимально необходимых прав, матрицу прав на объекты метаданных (справочники, документы, регистры), политику прав для объектов, не покрытых матрицей Дополнения к ТЗ, и способ реализации помарочных ограничений «чтение своих» без БСП.

## ADDED Requirements

### Requirement: Состав ролей конфигурации
Конфигурация SHALL содержать 6 новых ролей: `Профиль_Оператор`, `Профиль_Координатор`, `Профиль_Гид`, `Профиль_МенеджерПретензий`, `Профиль_Руководитель`, `Профиль_Аудитор` — профили групп доступа из раздела 6 Дополнения к ТЗ как самостоятельные роли (БСП не используется). Роль `Администратор` не изменяется; роль `Профиль_Администратор` не создаётся.

#### Scenario: Роли существуют после загрузки конфигурации
- **WHEN** конфигурация загружена из файлов и открыт каталог `Roles` метаданных
- **THEN** присутствуют 6 ролей с указанными именами и роль `Администратор`, и сумма ролей = 7

#### Scenario: Роль Администратор не изменена
- **WHEN** сравнить `Roles/Администратор.xml` и `Roles/Администратор/Ext/Rights.xml` с состоянием до изменения
- **THEN** файлы идентичны, UUID роли сохранён

### Requirement: Права на справочники
Роли SHALL предоставлять доступ к 10 справочникам из матрицы раздела 6 строго по этой матрице (приведена после сценариев); условные обозначения: Ч=View, П=Presentation, И=InteractionAdd, Изм=InteractionUpdate, В=ItemInput, «-» — отсутствие каких-либо прав. Ни одна из 6 ролей не SHALL получать полные права на справочники.

#### Scenario: Оператор редактирует справочник «своего» профиля
- **WHEN** пользователь с ролью `Профиль_Оператор` открывает список `Туристы`
- **THEN** команды «Добавить», «Изменить», «Ввод по строке» доступны и запись создаётся/изменяется

#### Scenario: Гид не изменяет справочники
- **WHEN** пользователь с ролью `Профиль_Гид` открывает список `ТурыМаршруты`
- **THEN** доступен только просмотр и «Ввод по строке», интерактивное изменение недоступно

#### Scenario: Нет прав — нет доступа
- **WHEN** пользователь с ролью `Профиль_Гид` пытается открыть справочник `ДоговорыСПоставщиками`
- **THEN** объект недоступен (нет даже View): в интерфейсе ссылка не отображается, программный запрос к объекту возвращает ошибку прав

### Requirement: Права на документы
Роли SHALL предоставлять доступ к 9 документам строго по матрице раздела 6 (обозначения те же, что и для справочников; приведена после сценариев).

#### Scenario: Гид создаёт, редактирование идёт платформенным замыканием
- **WHEN** пользователь с ролью `Профиль_Гид` создаёт документ `Инцидент` и сохраняет его
- **THEN** интерактивное добавление и ввод по строке доступны, сохранение проходит; самостоятельного права `Изм` матрица гидy не даёт, и права `Пров` (проведение) у него нет; право `Edit` присутствует автоматически — замыкание зависимости платформы (см. примечание о замыкании после матрицы)

#### Scenario: Претензии закрыты для всех, кроме менеджера и руководителя
- **WHEN** пользователь с ролью `Профиль_Оператор` пытается открыть журнал `ПретензияПоставщику`
- **THEN** объект недоступен (матрица «-»); пользователь с ролью `Профиль_Руководитель` может только читать

Примечание о замыкании (поправка 2026-10-24, заказчик подтвердил правило «доки не противоречат платформе»): у платформенного интерактивного добавления (`И`) есть обязательное замыкание зависимостей — ролям, получившим `И`, автоматически добавляются `Edit` и `Update`; отдельного права «интерактивное изменение» в платформе нет, его роль играет `Edit`. Поэтому запрет правки сохранённого документа на уровне прав для ролей с `И` невводим — правило «гид только регистрирует» обеспечивается порядком работы и формами, вне рамок ролевой модели. Для ролей без `И` (только `ЧВ`/`ЧПВ`) `Edit` не выдаётся, и сценарий «нет интерактивного изменения» выполняется правами честно.

### Requirement: Право обновления при проведении
Матрица ТЗ не содержит условного обозначения для права `Update`, необходимого для проведения документов. Для каждой роли, которой матрица даёт `InteractionUpdate` на документе, у которого включено проведение, SHALL дополнительно быть предоставлено право `Update` на этот документ; роли без `InteractionUpdate` право `Update` на документ не получают.

#### Scenario: Оператор проводит подтверждение услуги
- **WHEN** пользователь с ролью `Профиль_Оператор` выполняет проведение созданного им документа `ПодтверждениеУслуги`
- **THEN** проведение завершается успешно (право Update предоставлено)

#### Scenario: Руководитель не проводит
- **WHEN** пользователь с ролью `Профиль_Руководитель` пытается провести любой документ
- **THEN** команда проведения недоступна (нет Update и нет InteractionUpdate)

### Requirement: Права на регистры
Роли SHALL предоставлять права на регистры по матрице раздела 6 (приведена после сценариев): Ч=View; «Ч (свой)» трактуется как View для всех записей (см. отдельное требование о помарочных фильтрах). В матрице ТЗ отсутствует колонка «Администратор» — роль `Администратор` имеет полные права на все регистры по определению.

#### Scenario: Менеджер видит взаиморасчёты, оператор — нет
- **WHEN** пользователь с ролью `Профиль_МенеджерПретензий` читает регистр `ВзаиморасчётыПоПретензиям`, а пользователь с ролью `Профиль_Оператор` пытается сделать то же
- **THEN** менеджер получает записи, оператору объект недоступен

Матрица регистров:

| Регистр | Опер | Коор | Гид | Менедж | Рук | Аудит |
|---|---|---|---|---|---|---|
| Сведения СтатусыПодтверждений | Ч | Ч | - | Ч | Ч | Ч |
| Сведения ПараметрыУслуг | Ч | Ч | - | Ч | Ч | Ч |
| Сведения ГрафикПеремещений | Ч | Ч | Ч | Ч | Ч | Ч |
| Накопления ВзаиморасчётыПоПретензиям | - | - | - | Ч | Ч | Ч |
| Накопления ШтрафыИКомпенсации | - | - | - | Ч | Ч | Ч |
| Накопления KPIОператоров | Ч | Ч | Ч | Ч | Ч | Ч |

### Requirement: Помарочные ограничения «чтение своих»
Ограничения вида «Ч (свой)» (`KPIОператоров`, `ГрафикПеремещений`, «свой маршрут» гида) SHALL реализовываться фильтрами форм и настройками данных, а не платформенным RLS: роль даёт право View на весь регистр. Ограничение SHALL быть задокументировано как известное отличие от ТЗ (RLS требует групп доступа БСП, которые в самостоятельной конфигурации недоступны).

#### Scenario: Форма KPI отфильтрована «по себе»
- **WHEN** пользователь с ролью `Профиль_Оператор` открывает форму, отображающую `KPIОператоров`
- **THEN** по умолчанию форма показывает записи только по сотруднику, привязанному к текущему пользователю

#### Scenario: Программное чтение ограничено только View
- **WHEN** тот же пользователь получает доступ к полным данным регистра через разрешённый сценарий интерфейса
- **THEN** технически записи других сотрудников ему доступны (RLS нет) — это принятое ограничение курса, не дефект проверки прав

### Requirement: Права на ролевые подсистемы
Каждая роль-профиль SHALL получать право `View` на соответствующую ролевую подсистему и все её вложенные подсистемы (сопоставления приведены после сценариев) — этого достаточно для сборки рабочего места командным интерфейсом.

#### Scenario: Рабочее место собирается из разрешённых разделов
- **WHEN** пользователь с ролью `Профиль_Координатор` открывает командный интерфейс
- **THEN** виден раздел `КоординаторЛогистики` с вложенными пунктами, раздел `ОператорСопровождения` не виден

Сопоставления: `Профиль_Оператор` → `ОператорСопровождения`; `Профиль_Координатор` → `КоординаторЛогистики`; `Профиль_Гид` → `ГидНаМаршруте`; `Профиль_МенеджерПретензий` → `МенеджерПоПретензиям`; `Профиль_Руководитель` → `РуководительНаправления`; `Профиль_Аудитор` → все пять бизнес-подсистем, кроме `АдминистраторИС`. Доступ к `АдминистраторИС` обеспечивает существующая роль `Администратор`.

### Requirement: Объекты вне матрицы ТЗ
Для фактических объектов конфигурации, не перечисленных в матрице раздела 6 Дополнения к ТЗ (бизнес-процессы, задачи, обработки, пользователи, часть регистров, константа, перечисления, ЧХ, техническая НСИ), SHALL применяться политика прав, приведённая после сценариев; она закрывает функциональные сценарии рабочих мест и не выдаёт профилям полных прав.

#### Scenario: Техническая НСИ читается всеми
- **WHEN** пользователь с ролью `Профиль_Аудитор` открывает справочник `СтраныМира`
- **THEN** просмотр доступен, добавление/изменение — нет

#### Scenario: Настройки интеграций закрыты для профилей
- **WHEN** пользователь с ролью `Профиль_Оператор` пытается прочитать регистр `НастройкиИнтеграций`
- **THEN** объект недоступен (права имеет только роль `Администратор`)

#### Scenario: Обработка по рабочему месту
- **WHEN** пользователь с ролью `Профиль_Координатор` открывает обработку `ПересчётТайминговМаршрутов`, а пользователь с ролью `Профиль_Гид` пытается открыть её же
- **THEN** координатор может запустить обработку, гиду она недоступна

Политика для объектов вне матрицы:

1. Планы видов характеристик (`ДополнительныеРеквизитыТуриста`, `ДополнительныеРеквизитыУслуг`), справочники `Валюты`, `ЕдиницыИзмерения`, `СтраныМира` — View+Presentation всем профилям, дополнительно ItemInput всем (техническая НСИ для ввода по строке); редактирование — только `Администратор`. Перечисления прав на объекты не имеют (механизм ролей платформы их не поддерживает) — их чтение доступно всем аутентифицированным пользователям без настройки ролей.
2. Справочник `Пользователи` — View+Presentation всем профилям (реквизиты автор/ответственный в документах), редактирование — только `Администратор`.
3. Константа `ПорогСогласованияРуководителем` — View всем профилям, изменение — только `Администратор`.
4. Бизнес-процессы (4) и `ЗадачаИсполнителя` — View+Presentation+Update профилям `Оператор`, `Координатор`, `МенеджерПретензий`, `Руководитель` (согласование задач); `Гид` — View+Presentation; `Аудитор` — прав не получает.
5. Регистры сведений: `АдресацияЗадач`, `СтатусыИнцидентов` — View всем бизнес-профилям; `ИсторияОбработокЗапросов` — View профилям `Оператор`, `МенеджерПретензий`, `Руководитель`, `Аудитор`; `СрокиКонтроля` — View профилям `Оператор`, `Координатор`, `Руководитель`, `Аудитор`; `НастройкиИнтеграций` — только `Администратор`.
6. Обработки: `ПросроченныеСрокиИSLA` — View+Presentation+Use профилям `Оператор`, `Руководитель`; `ПересчётТайминговМаршрутов` — `Координатор`; `ФормированиеЗапросовПоставщикам` — `Оператор`; `СводкаСтатусов` — View+Presentation+Use профилям `Оператор`, `Координатор`, `МенеджерПретензий`, `Руководитель`, `Аудитор`; `ОбменСФайлами` — только `Администратор`.

### Requirement: Отсутствие новых субъектов в DefaultRoles
Изменение SHALL NOT назначать роли-профили в `DefaultRoles` конфигурации: назначение ролей конкретным пользователям выполняется вручную при проверке сценариев, новые пользователи не получают автоматических прав.

#### Scenario: DefaultRoles пуст
- **WHEN** загрузить конфигурацию и открыть свойства конфигурации
- **THEN** `DefaultRoles` пуст, как до изменения
