# Design

## Context

См. `proposal.md` — Why; требования — `specs/access-roles/spec.md`. Текущее состояние, важное для «как»:

- Формат исходников: `src/КурсоваяРабота/Roles/<Имя>.xml` (описание роли) + `src/КурсоваяРабота/Roles/<Имя>/Ext/Rights.xml` (права). Единственная существующая роль `Администратор` прав-записей в `Rights.xml` не имеет — полнота обеспечивается флагами `setForNewObjects=true`, `setForAttributesByDefault=true`.
- Состав конфигурации регистрируется в `Configuration.xml` (секция `<Role>Администратор</Role>`, строка ~259) — новые роли должны попасть в состав.
- В проекте есть tooling-скиллы: `role-compile` (роль из JSON-описания прав), `role-validate`, `cf-validate`, а также пайплайн загрузки `db-load-xml` → `db-update`.
- Конфигурация самостоятельная (без БСП), файловая ИБ; групп доступа и RLS платформы нет.
- Подсистемы уже разведены по рабочим местам (`ОператорСопровождения`, `КоординаторЛогистики`, `ГидНаМаршруте`, `МенеджерПоПретензиям`, `РуководительНаправления`, `АдминистраторИС`) с командными интерфейсами — права `View` на подсистему достаточно для видимости раздела.

## Goals / Non-Goals

**Goals:**
- Механическая генерируемость 6 `Rights.xml` из матрицы спеки без ручного перебора GUID в XML.
- Проверяемость прав на живых пользователе/сессиях 1С (сценарии спеки).
- Сохранение инварианта «роль `Администратор` и её UUID не меняются».

**Non-Goals:**
- БСП, группы доступа, RLS, шифрование, журнал регистрации, парольная политика из раздела «Требования по безопасности» Дополнения к ТЗ — вне рамок (часть невозможна в файловой ИБ, часть требует сервера).
- Назначение ролей тестовым пользователям ИБ как часть метаданных (пользователи — данные; проверяем вручную/скриптом, в Git не попадает как конфигурация).
- Создание отчётов СКД «для строки матрицы» — отчётов в конфигурации нет, строку матрицы считаем неприменимой (зафиксировано в proposal).

## Decisions

### D1. Профили = 6 самостоятельных ролей, имена `Профиль_*`
Альтернатива — справочник-«группы доступа» собственной реализации — отвергнута: переизобретение БСП ради курсового неоправданно; ТЗ и `docs/Оставшиеся-задачи.md` уже называют эти имена. Идентификаторы ролей — русские, как в ТЗ (`Профиль_Оператор` и т.д.), метаданные конфигурации целиком кириллические.

### D2. Конвертация условных обозначений ТЗ в DSL-идентификаторы role-compile (уточнено 2026-10-24 по dsl-reference.md — ранее таблица ссылалась на несуществующие имена)
| ТЗ | DSL-права в objects-строках |
|---|---|
| Ч | `Read` (для Subsystem — `View`, для DataProcessor — `View`) |
| П | `View` |
| И | `Insert, InteractiveInsert` |
| Изм | `Edit, Update` — отдельного «интерактивного изменения» у платформы нет, гейт редактирования — `Edit`; для ролей с `И` `Edit`+`Update` приходят замыканием независимо от `Изм` |
| В | `InputByString` (+ замыкание до `View`) |
| Р | `InteractiveDeletionMarking`/`InteractiveDelete` — в 6 профилях не встречается (только колонка Администратор) |
| Д | `InteractiveDeleteMarked` — там же |
| Пров (нет в матрице ТЗ) | `Posting, InteractivePosting, InteractivePostingRegular` на документах; `Update` на БП/задачах — по правилу спеки («Изм» ∩ документ с `<Posting>Allow</Posting>`) |
| Use (обработки) | `Use` |

Права на табличные части/реквизиты не настраиваем: ТЧ в конфигурации нет; `setForAttributesByDefault` оставляем по умолчанию DSL (`true`) — права реквизитов наследуются от прав на объект (ruling 2026-10-24: отказывать в наследовании означало бы сломанные формы).

### D3. Генерация через `role-compile`, затем `role-validate`
JSON-описание прав (объект метаданных → список прав) для каждого профиля ведём одним машиночитаемым артефактом в `openspec/changes/add-access-roles/` (например `roles-matrix.json`) — он остаётся следствием спеки для переноса в базу и повторной генерации при изменении матрицы. Ручное редактирование GUID в `Rights.xml` запрещено: при ошибке правим JSON и перегенерируем. Альтернатива (писать Rights.xml руками) отвергнута: записи прав содержат ссылки на UUID объектов, велик риск опечатки без валидации.

### D4. Регистрация состава и загрузка
Новые роли добавляются в `<Role>`-состав `Configuration.xml` инструментами `role-compile`/`cf-edit`; загрузка — `db-load-xml` + `db-update` (файловая ИБ, обновление без данных безопаснее делать копией `.dt`-бэкапа — см. `db-dump-dt`). Откат — `git revert` исходников + повторная загрузка; сами роли в базе при загрузке конфигурации «сбрасываются» к файлам.

### D5. Право `Update` для проведения
Список проводимых документов определяется чтением `Documents/*.xml` (признак `<Posting>Allow</Posting>`). Правило из спеки: профиль получает право проведения ровно на те проводимые документы, где у него `Изм`. Ожидаемо: Оператор — `ЗаказПоставщику`, `ПодтверждениеУслуги`, `ЗаявкаТуристаНаМаршруте`; Координатор — `МаршрутныйЛист`, `СобытиеМаршрута`, `КорректировкаМаршрута`; Менеджер — `Инцидент`, `ПретензияПоставщику`, `АктОКомпенсации`. Гид не проводит (нет Изм) — согласуется с его матрицей `ЧПИВ`.

### D6. Проверка на живых пользователях
Верификация — не только статическая: создаём в ИБ 6 проверочных пользователей (по профилю + один с `Администратор`), для каждого прогоняем ключевые сценарии спеки (интерактивно через `db-run` или `web-test`): видимость разделов, недоступность чужих объектов, проведение «своих» документов. Это единственный способ проверить поведение командного интерфейса и `ПравоДоступа` из смежных спеков.

## Risks / Trade-offs

- [Матрица ТЗ расходится с реальными объектами] → политика «вне матрицы» зафиксирована требованием спеки; список расхождений — в proposal; при загрузке `cf-validate`/синтаксическая проверка не поймает логическую ошибку матрицы → проверяем сценариями D6.
- [`setForNewObjects=true` у `Администратор` не даёт автоматических прав новым ролям друг на друга] → не риск, но следим: `role-compile` не должен случайно выставить эти флаги в профилях (иначе профили станут полными).
- [Помарочные фильтры форм завязаны на привязку пользователя к `Сотрудники`] → если у проверочного пользователя нет связи, форма «своего KPI» покажет пустой/весь список — это ожидаемое поведение фильтра, не права; фиксируем в отчёте проверки.
- [Опечатки в GUID при генерации] → митигция D3 (перегенерация из JSON) + `role-validate` перед загрузкой.
- [Нет прав на `Интерфейс`] → командный интерфейс filtered по подсистемам; отдельного права на `ClientApplicationInterface` не добавляем — стандартное поведение платформы (все с любым доступом видят интерфейс, пустые разделы скрываются по правам подсистем).

## Migration Plan

1. Сгенерировать 6 ролей из `roles-matrix.json` (`role-compile`), зарегистрировать в составе.
2. `role-validate` всех новых ролей + `cf-validate` конфигурации.
3. Бэкап ИБ (`db-dump-dt`) → `db-load-xml` → `db-update`.
4. Создать проверочных пользователей, прогнать сценарии спеки (D6).
5. Обновить `docs/Оставшиеся-задачи.md` (закрыть остаток этапа 3).
Откат: git revert + загрузка конфигурации из предыдущего коммита (структура метаданных обратима, данные не трогаются).

## Open Questions

- Точный перечень проводимых документов (для D5) — уточняется чтением XML на шаге реализации; на матрицу прав вне «Изм»-пересечения не влияет.
