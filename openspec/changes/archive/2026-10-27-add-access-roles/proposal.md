# Proposal

## Why

Сегодня в конфигурации существует единственная роль `Администратор` (полные права через `setForNewObjects=true`), то есть любой пользователь базы имеет неограниченный доступ. Дополнение к ТЗ (раздел 6 «Моделирование ролей, прав доступа и сценариев работы пользователей») требует ролевую модель «минимально необходимых прав» из шести пользовательских профилей; без неё ни один сценарий типового рабочего места (оператор, координатор, гид, менеджер, руководитель, аудитор) не проверяем, а требование остатка этапа 3 (`docs/Оставшиеся-задачи.md`) закрыто не будет.

## What Changes

- Создаются **6 новых ролей** конфигурации: `Профиль_Оператор`, `Профиль_Координатор`, `Профиль_Гид`, `Профиль_МенеджерПретензий`, `Профиль_Руководитель`, `Профиль_Аудитор`. Права — по матрице раздела 6 Дополнения к ТЗ (справочники, документы, регистры) плюс политика для объектов, не покрытых матрицей.
- Роль `Профиль_Администратор` из ТЗ **не создаётся**: функции администратора ИС выполняет существующая роль `Администратор` (её состав и UUID не меняются). Это решение заказчика, оформленное как расхождение с ТЗ.
- Для каждого профиля даётся `View` на соответствующую ролевую подсистему (`ОператорСопровождения`, `КоординаторЛогистики`, `ГидНаМаршруте`, `МенеджерПоПретензиям`, `РуководительНаправления`, `АдминистраторИС` — последней только у `Администратор`), чтобы командный интерфейс рабочего места собирался из разрешённых разделов.
- Помарочные ограничения «Чтение (своих)» (KPIОператоров, ГрафикПеремещений, «свой маршрут» у гида) реализуются **не RLS, а фильтрами форм/настройками данных** — RLS без БСП недоступен; ограничение фиксируется в спеке.
- Отдельным разделом спеки и proposal перечисляются **расхождения реализации с Дополнением к ТЗ** (см. ниже «Расхождения с ТЗ»).

## Capabilities

### New Capabilities

- `access-roles`: ролевая модель доступа конфигурации — состав ролей-профилей, матрица прав на объекты метаданных, политика для объектов вне матрицы ТЗ, адаптация помарочных ограничений, известные расхождения с Дополнением к ТЗ.

### Modified Capabilities

*(нет — требования `navigation-and-commands` о подчинении команд правам доступа не меняются, роли лишь заполняют существующий механизм)*

## Impact

- `src/КурсоваяРабота/Roles/` — 6 новых каталогов ролей (`<Имя>.xml` + `Ext/Rights.xml`); существующая `Roles/Администратор.xml` и её `Rights.xml` не трогаем (UUID `527785c9-…` неприкосновенен).
- Загрузка в ИБ: `LoadConfigFromFiles` + обновление конфигурации базы; назначение ролей тестовым пользователям ИБ (в том числе справочник `Пользователи`).
- Документация: `docs/Оставшиеся-задачи.md` (остаток этапа 3 закрывается), фиксация принятых заказчиком расхождений.
- Тестирование сценариев: проверки «команда/форма недоступна без права» из `navigation-and-commands`, `data-processors`, `data-exchange` получают реальный субъект проверки — профиль без права.

## Расхождения с Дополнением к ТЗ (зафиксированы заказчиком)

1. **«Профили групп доступа» → отдельные роли.** Механизм групп доступа — функциональность БСП; конфигурация самостоятельная, БСП не подключается. Профили реализуются как 6 ролей с именами из ТЗ (`Профиль_*`).
2. **`Профиль_Администратор` не создаётся** — используется существующая роль `Администратор` (полные права).
3. **«Все СКД-отчёты» в матрице** — в конфигурации нет ни одного объекта `Report`; строка матрицы неприменима. Отчётные сценарии закрыты обработками (`СводкаСтатусов` и др.), их права задаёт политика вне-матричных объектов.
4. **Матрица ТЗ не покрывает** реальные объекты: 4 бизнес-процесса, `ЗадачаИсполнителя`, 5 обработок, `Пользователи`, регистры `АдресацияЗадач`, `ИсторияОбработокЗапросов`, `НастройкиИнтеграций`, `СрокиКонтроля`, `СтатусыИнцидентов`, константу `ПорогСогласованияРуководителем`, 15 перечислений, 2 плана видов характеристик, накопительные регистры частично. Для них принимается предложенная политика прав (раздел «Объекты вне матрицы ТЗ» спеки).
5. **«Чтение (своих)»** — platform RLS требует групп доступа (БСП); реализуется фильтрами форм, роль даёт чтение регистров целиком.
6. **В таблице «Регистры и отчёты» ТЗ отсутствует колонка «Администратор»** — полагаем, что `Администратор` имеет там полные права (он имеет полные права на всё по определению роли).
7. Имена 10 справочников и 9 документов из матрицы совпадают с метаданными один-в-один; табличных частей у объектов нет, отдельного строк-прав на ТЧ не требуется. Основной `Техническое задание.doc` ролевой матрицы не содержит — единственный источник ролевых требований = Дополнение к ТЗ, раздел 6.
8. (добавлено 2026-10-24) «Интерактивное добавление без изменения» (строки `ЧПИВ` гида) невводимо на уровне прав: у платформы `И` обязательное замыкание зависимостей до `Edit`+`Update`, а отдельного права «интерактивное изменение» нет (его роль играет `Edit`). Сценарий спеки переформулирован; запрет правки после сохранения — вопрос порядка работы и форм, не ролей.
9. (добавлено 2026-10-25) В конфигурацию добавлена инфраструктурная роль `ТестоваяИнфраструктура` (3 права уровня конфигурации: открытие внешних обработок, технологический режим, режим основного окна) — без неё автоматическая проверка прав на тестовых пользователях невозможна на файловой ИБ. Назначается только тестовым учётным записям; продуктовые профили не затронуты. Решение заказчика: ТЗ корректируемо, если в ходе разработки выясняется нецелесообразность его молчания об инструментах тестирования.
