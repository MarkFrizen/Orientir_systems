# Design

## Context

См. `proposal.md` — Why. Состояние на момент планирования:

- Правила проведения есть для восьми документов (р.5.1.1–5.1.8). Для `СобытиеМаршрута` правил в источнике нет.
- `ВзаиморасчётыПоПретензиям` (измерения: претензия, поставщик, договор, валюта; ресурсы: сумма требования, сумма удовлетворения), `ШтрафыИКомпенсации` (инцидент, поставщик, вид компенсации, валюта; суммы туристу и с поставщика), `KPIОператоров` (сотрудник, вид операции; количество, время обработки) — оборотные регистры накопления с ресурсами.
- `ГрафикПеремещений` — регистр **сведений** с измерениями (маршрутный лист, событие, турист, объект, тип события) и реквизитами времени. Ресурсов нет.
- `ЗадачаИсполнителя` уже адресуется через `АдресацияЗадач` (измерение `Исполнитель`) — механизм задач настроен, писать нужно только создание и закрытие.
- Модули объектов документов содержат `ПередЗаписью` с правилами записи; общие модули `РасчётКомпенсаций`, `КонтрольСроков`, `РаботаСДатамиИЧасовымиЗонами` реализованы.
- База файловая, одновременная работа — единицы пользователей.
- Автотесты в проекте работают: xdd-смоук `tests/vanessa/run-xdd-smoke.ps1` обходит формы конфигурации (83/83), `tests/exchange/run-exchange-tests.ps1` прогоняет сценарии обмена (8/8), `epf/run-check.ps1` даёт вердикт PASS по демо-набору. Не работает только Vanessa **BDD**-раннер 6.9.5 (issue #1160), которым проект не пользуется; xddTestRunner на 8.3.27 работает.
- Готовый EPF `тесты_ПроведениеДокументов.epf` лежит в `build/vanessa/add-6.9.5/tests/smoke/` и годится как дымовой тест проведения.
- Образец драйвера поведенческих тестов — `epf/ТестОбмена` + `tests/exchange/run-driver.ps1`: сценарий запускается внешней обработкой, отчёт содержит строки проверок и вердикт `PASS`/`FAIL`, раннер возвращает код 0/1/2.

## Goals / Non-Goals

**Goals:**

- Движения регистров при проведении девяти документов и корректная отмена проведения.
- Общий примитив блокировок; запись и очистка движений — в модулях объектов документов; создание задач — отдельный модуль.
- Четыре массовые операции с понятным результатом по каждому объекту и с проверкой прав перед выполнением.
- Запросы, пригодные для роста объёмов: параметризованные, без выборки «всё в память».

**Non-Goals:**

- Карты маршрутов бизнес-процессов и автопереходы — отдельный change (BPM-механика).
- Отчёты на СКД, интеграции, роли и профили групп доступа. Проверка прав через `ПравоДоступа` в объёме; отказ без прав проверяется только после появления профилей.
- Изменение правил записи (`ПередЗаписью`) — они уже реализованы и покрыты `data-validation`.

## Decisions

### D1. Проведение — в модуле объекта документа, примитивы — в общем модуле

`ОбработкаПроведения` живёт в модуле объекта каждого документа: так сохраняется типовая схема, отладка идёт по конкретному документу, а `ОтменаПроведения` симметрична. Общий модуль `ПроведениеДокументов` держит единственный примитив — установку управляемых блокировок по регистрам.

Универсальные помощники для запис и очистки движений оказались невозможны, и это выяснилось на практике. У регистра сведений, подчинённого регистратору, набор записей фильтруется только по регистратору — фильтр по измерению платформа не принимает, поэтому `ЗаписатьСтатус` падал. Оборотный регистр накопления в обход регистратора через менеджер записи вообще не пишется, поэтому `ЗарегистрироватьKPI` был нерабочим по построению. Оба удалены; документ сам ведёт свои наборы записей. Создание задач вынесено в отдельный модуль `ЗадачиИсполнителям`.

Альтернатива — единый диспетчер проведения с регистрацией обработчиков в общем модуле. Отклонена: ломает типовую схему, усложняет отладку и не даёт выигрыша при восьми документах.

### D2. `ГрафикПеремещений` остаётся регистром сведений

Раздел 5.2.1 называет его регистром остатков, но фактическая структура (измерения события и реквизиты времени, без ресурса) описывает расписание, а не сальдо. Движение = запись, замена и удаление записей по регистратору. Переделка в регистр накопления потребовала бы ресурса, пересчёта остатков и миграции данных, не изменив ни одного сценария.

Проверка пересечений выполняется запросом по измерениям (турист, объект) и реквизитам времени, а не остатками регистра.

### D3. `СобытиеМаршрута` не формирует движений

В разделе 5.1 правила для него отсутствуют, а события попадают в график через `МаршрутныйЛист`, который и является регистратором. Решение: проведение документа допускается (он источник событий и используется формами), но движений не создаёт. Альтернатива — запретить проведение свойством `Проведение = Запретить`; отклонена, потому что документ планируется использовать как самостоятельный факт события при корректировках.

### D4. Отмена проведения удаляет движения регистратора

Регистры оборотные и сведения; сторнирующие записи усложнили бы каждый запрос и потребовали бы фильтра «не сторно». Стандартный механизм 1С — удаление движений по регистратору — сохраняется. Для `ГрафикПеремещений` удаление и повторная запись дают идемпотентность при повторном проведении.

### D5. Порядок блокировок фиксирован

Блокировки берутся сначала по регистрам накопления (взаиморасчёты, штрафы, KPI), затем по регистрам сведений (статусы, параметры, график). Порядок одинаков во всех документах — это исключает взаимную блокировку при встречном проведении, например претензии и акта.

Режим — **исключительный**. Разделяемую блокировку с последующей записью в тот же регистр файловая база не переживает: транзакция ждёт повышения собственного блокировки и висит без сообщения об ошибке и без дампа. Это единственная причина, по которой проведение в этой конфигурации блокирует регистры именно исключительной блокировкой.

### D6. Массовые операции фиксируются по объектам, а не одной транзакцией

Обработка обрабатывает каждый объект в своей транзакции и собирает результат: создано, пропущено, ошибка. Общий откат недопустим — одна битая заявка не должна отменять четыреста корректных. Это тот же принцип, что уже принят для частичной загрузки CSV в `data-exchange`.

### D7. Обработки встроенные

Четыре обработки размещаются в `DataProcessors` и включаются в подсистемы: формирование запросов — в «Заказы поставщикам» оператора сопровождения, пересчёт таймингов — в «Корректировки» координатора логистики, просрочки — в «Эскалации» руководителя направления, сводка статусов — в «Отчёты KPI» руководителя направления. Каждая перед выполнением проверяет право на изменяемый (для сводки — на читаемый) объект через `ПравоДоступа` и отказывает исключением без раскрытия состава данных. Внешние обработки в `epf/` остаются служебными: наполнение НСИ, проверка набора, тест обмена, драйвер автотестов.

### D8. KPI пишется при проведении документов, а не при закрытии задач БП

Раздел 5.2.4 привязывает KPI к закрытию задач бизнес-процессов, но карты БП пустые, и задач в процессе не возникает. Пока KPI регистрируется при проведении: `ОбработанаЗаявка` — при проведении `ПодтверждениеУслуги`, `ОбработанЗапрос` — при проведении `ЗаявкаТуристаНаМаршруте`, `УрегулированИнцидент` — при проведении `АктОКомпенсации`. Время обработки считается от даты создания документа до даты проведения. При реализации карт БП источник переедет на задачи — требования спеки при этом не меняются, меняется только место вызова.

### D9. Проверка проведения автоматизируется драйвером, а не чек-листом

Проведение нельзя проверить смоуком открытия форм — он смотрит только, что форма открылась. Поэтому поведение проверяется внешней обработкой-драйвером `ТестПроведения` по образцу `ТестОбмена`: сценарий на документ выполняет полный цикл «провести → сверить записи регистров и статусы → провести повторно → сверить отсутствие дублей → отменить → сверить пустоту», пишет построчный отчёт и итоговый вердикт. Раннер `tests/posting/run-posting-tests.ps1` прогоняет сценарии по порядку зависимостей и печатает `ИТОГО: N/N`.

Ручные проверки остаются только там, где нужен человек: читаемость сообщений об ошибках, подсказки, внешний вид. Альтернатива — проверять всё руками по чек-листу — отклонена: невоспроизводимо, не даёт кода возврата и не ловит регрессию при следующих изменениях.

### D10. Запросы параметризованы и не тянут лишнего

Все запросы строятся по периоду и отбору, передаваемому из формы, с явным списком полей; виртуальные таблицы остатков не используются (для регистра сведений они неприменимы). Для сальдо — свёртка движений по претензии, для KPI — группировка по сотруднику и виду операции. Жёсткая привязка к конкретным документам и датам в коде отсутствует: обработчик получает массив ссылок или параметры отбора.

## Risks / Trade-offs

- [KPI по задачам БП невозможен, пока карты пустые] → регистрация при проведении документов, перенос на задачи — в change с BPM; спека описывает только показатель, не источник.
- [Порог `ПорогСогласованияРуководителем` в демо равен нулю] → при реализации заполнить демо-значением (10 000) и проверить оба случая; иначе сценарий согласования не воспроизводится.
- [`СобытиеМаршрута` без правил проведения может потребовать движений при уточнении ТЗ] → решение D3 зафиксировано, изменение локализуется в одном модуле объекта.
- [Файловая ИБ и управляемые блокировки ограничены одним процессом] → блокировки по ключам и короткие транзакции; конкуренции на учебных объёмах нет.
- [xdd-смоук проверяет только открытие форм и не увидит ошибок проведения] → поведение покрывается драйвером `ТестПроведения` с построчными проверками и вердиктом, смоук остаётся регрессией по формам.
- [Драйвер сам создаёт документы и может испортить демо-набор] → сценарии берут существующие документы демо-набора, работают в транзакции и в конце отменяют проведение; при отсутствии данных сценарий падает с подсказкой запустить `epf/run-fill.ps1`.

## Migration Plan

- Данные не мигрируют: существующие документы демо-набора непроведённые, после реализации их можно провести.
- Порядок реализации: общий модуль примитивов → документы от менее связанных к более связанным (`ЗаказПоставщику`, `ПодтверждениеУслуги`, `МаршрутныйЛист`, `КорректировкаМаршрута`, `ЗаявкаТуристаНаМаршруте`, `Инцидент`, `ПретензияПоставщику`, `АктОКомпенсации`) → обработки → запросы.
- Откат: отмена проведения документов удаляет движения; при необходимости — revert коммита, структура метаданных не меняется.
