# Design

## Context

См. proposal.md — Why. Текущее состояние, важное для подхода:

- ИБ файловая, платформа 8.3.27 учебной версии (лимит 2048 МБ, строка ≤ 1024 символов, блокировки — в пределах одного процесса); серверных механизмов в коде нет и добавлять не будем.
- Проведение 8 документов, регистровые контракты и статусные переходы уже задокументированы в спеках `document-posting` и `business-processes` — отладка сверяет код со спекой, а не изобретает критерии.
- Ролевая модель реализована: 6 профилей + `Администратор` + `ТестоваяИнфраструктура` (спека `access-roles`); RLS нет намеренно, ограничения «своих» — фильтрами форм.
- Инфраструктура прогонов уже есть: внешние обработки `epf\ЗаполнениеНСИ`, `epf\ПроверкаДанных`, `epf\ТестОбмена`, `epf\ТестПроведения`, `epf\ПроверкаДоступа`; запуск через `1cv8.exe` с консольным выводом в лог; дампы `Ошибка_*.zip` — основной сигнал сбоя (правило 7 AGENTS.md).
- Известные кандидаты на дефекты из разведки: недетерминированный штамп KPI (`ТекущаяДатаСеанса() - Дата`), отсутствие прав у роли `Администратор` в XML при полном наборе в ИБ (расхождение источника и базы), голые `ВызватьИсключение` в пользовательских путях обработок.

## Goals / Non-Goals

**Goals:**
- Воспроизводимые прогоны: каждый класс проверок запускается командой/обработкой и оставляет машинночитаемый лог, а не только слова «проверено».
- Дефекты, найденные отладкой, исправлены в этом же изменении; фикс проверяется повтором того же прогона.
- Ручная часть (права, UI-отказы) формализована в отдельном плане тестирования — с шагами и ожидаемым результатом, чтобы «нет прав» проверялось одинаково руками и в отладке.

**Non-Goals:**
- Изменение контрактов спека (`document-posting`, `data-validation`, `access-roles`) — только приведение кода к ним.
- Клиент-серверный развёртывание, фоновые задания, тестирование веб-клиента на сервере приложений.
- Нагрузочное тестирование «на износ»: объёмные прогоны проверяют отсутствие сбоя, а не производительность.

## Decisions

### D1. Двухслойный прогон: автоматика для данных, руки для прав

Автоматизируемое (движения, статусы, ошибки записи, CSV-дубли, объём) — существующими обработками `ТестПроведения`/`ТестОбмена`/`ПроверкаДанных` в пакетном режиме (`1cv8.exe ... /RunExternalEOF` с логом). Сценарии «нет прав» автоматикой в одной ИБ не воспроизводятся (сеанс под логином — интерактивный), поэтому проверяются вручную по плану тестирования, а `ПроверкаДоступа` фиксирует только корректность настройки ролей. Альтернатива (Vanessa/авто-UI) отвергнута: хрупко, время, учебная лицензия.

### D2. Критерий «корректность движений» = снимок ожиданий из спека

Для демонстрационного набора заранее фиксируется ожидаемый набор записей каждого из 11 регистров-получателей и статусов документов (таблица в тестовых фикстурах `tests\posting`). Прогон сравнивает фактические движения с ожиданием запросами, отличие = дефект или устаревшее ожидание (решает человек, не авто). Альтернатива «глазами по одному документу» отвергнута: не пошаговая отладка, а лотерея.

Факт, уточнённый при выполнении: `epf\ЗаполнениеНСИ` создаёт 20 документов **без проведения** (только `.Записать()`), поэтому снимок фиксирует ожидаемое состояние не «как лежит», а **после прогона сценариев проведения** `ТестПроведения` по цепочкам; снимок привязан к шагам сценария (post-order → post-confirmation → … → post-compensation-act), а не к базе целиком.

### D3. Статусная сверка — сквозные цепочки, включая отмену проведения

Каждый статус из `СтатусыЗаявок`/`СтатусыИнцидента`/`СтатусыЗаказа` проверяется переходом туда и обратно (проведение → отмена → перепроведение), поскольку реализован откат статусов (`ВРаботе`). Односторонняя проверка не поймала бы дефекты отката.

### D4. Политика отказа: `Сообщить`+`Отказ` на пользовательских путях, `ВызватьИсключение` — только программные ошибки

Правило фиксации найденного: если нештатная ситуация достижима действиями пользователя, путь должен заканчиваться сообщением (паттерн `ПравилаЗаписи`), а не исключением; `ВызватьИсключение` остаётся для ошибок программирования и нарушенной инвариантности (по образцу `ОбменСФайлами:1896` «Запись отклонена правилами объекта»). Чинится по месту, без единого перехватчика-«фильтра» — альтернатива с глобальным `ПередОбработкой/ПослеОбработки` отвергнута: скрыла бы реальные причины.

### D5. Детерминизм KPI: штамп оборота = дата документа-регистратора

Текущая запись `KPIОператоров` с `ТекущаяДатаСеанса()` делает повторный прогон непроверяемым (D2). Фикс: использовать дату документа. Это не меняет специкацию (спека не оговаривает источник времени) и убирает псевдослучайность из сверок.

### D6. Объёмная проверка файлового режима — масштабирование в 10 раз, не «до упора»

`ЗаполнениеНСИ` получает параметр кратности (~200 документов, ~5000 записей регистров): проверяются лимит объёма (до 2048 МБ с запасом), время прогона, отсутствие сбоя; после прогона база возвращается к демонстраческому набору из `.dt`-бэкапа (`db\backup`). «До заполнения лимита» отвергнуто: разрушает базу, результат невоспроизводим.

## Risks / Trade-offs

- [Пакетный запуск упирается в модальные диалоги/зависания] → перед каждым прогоном проверять отсутствие живых `1cv8*`, читать свежий `Ошибка_*.zip` по правилу 7; обработки запускаются без диалогового режима (`/ЗаписьЖурнала`).
- [Ожидания D2 разойдутся со спекой при фиксе] → приоритет спека: код правится под спеку; расхождение спеки с платформенной реальностью файловой ИБ — стоп и вопрос заказчику (правило 4 AGENTS.md), не молчаливая правка спеки.
- [Масштаб x10 + обмен может превысить учебный лимит] → замеры после каждого шага масштабирования, откат к `.dt`; вердикт проверки фиксирует байты.
- [Ручная проверка прав зависит от настройки пользователей ИБ] → чек-лист настройки (логины → роли) в плане тестирования; `ПроверкаДоступа` верифицирует соответствие `ИмяПользователяИБ` прежде, чем делать выводы об отказе доступа.
- [Фиксы найденных дефектов непредсказуемы по объёму заранее] → скоуп меняется только через обновление tasks.md/specs в этом же изменении; если фикс требует смены спека — отдельный change по решению заказчика.

## Migration Plan

1. Бэкап `.dt` до начала прогонов (уже ведётся в `db\backup`).
2. Исправления — итерациями «прогон → дефект → фикс → повтор прогона»; статический контроль `1c-lsp-diagnostics` (severity 1) перед каждой `LoadConfigFromFiles` (правило 8 AGENTS.md).
3. Откат: `.dt`-бэкап + git; изменения кода не меняют структуру метаданных, миграции данных нет.

## Open Questions
