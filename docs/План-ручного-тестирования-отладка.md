# План ручного тестирования — отладка и стабилизация (п. 3 ТЗ)

Дата: 2026-10-27. Ревизия: v1.
Область: те же части, что покрывает изменение OpenSpec `debug-and-stabilize` (спеки `error-resilience`, `file-mode-operation`, контракты `document-posting`/`data-validation`/`access-roles`). Документ вне спецификации; используется при выполнении задач 3.5, 4.x, 5.2 того изменения.

## 0. Общие положения

**Предварительные условия (обязательны перед каждой сессией):**
1. Свежий `.dt`-бэкап базы в `db\backup`, запись его даты в журнал прогона.
2. Все сеансы 1С закрыты: `Get-Process 1cv8*` пуст (лицензия на 1 место, прогоны строго последовательные).
3. База наполнена `epf\ЗаполнениеНСИ` (демонстрационный набор), состояние подтверждено `epf\ПроверкаДанных`.
4. Учётки и роли настроены по эталону `docs\Регрессия-прав.md` (раздел 2): шесть профильных учёток, пустые пароли, `ТестоваяИнфраструктура` у тестовых, «Защита от опасных действий» снята.
5. Понятие «сбой» для плана: новый `Ошибка_*.zip` в корне проекта после действия (читать `report.json`, правило 7 AGENTS.md), зависание > 2 мин, молчаливое завершение без результата там, где ожидается отчёт/сообщение.

**Протокол записи:** в таблице каждого чекпойнта колонки «Факт» и «Вердикт» заполняются на месте: `PASS` / `FAIL(№ дефекта)` / `BLOCKED(причина)`. Скриншоты/выгрузки — в `<папка прогона>\evidence\`.

## A. Движения регистров и статусы (сквозная цепочка)

Проверка движений: форма «Отчёт по регистрациям» нужного регистра либо консоль запросов (`ВЫБРАТЬ ... ИЗ РегистрыСведений.<Имя> КАК тс ГДЕ тс.Регистратор = &Док`). Каждое действие выполняется на новых объектах цепочки, не ломая демонстрационный набор (пометка «ТЕСТ» в наименовании).

| № | Шаг (действия вручную) | Ожидаемый результат | Факт | Вердикт |
|---|---|---|---|---|
| A1 | Создать и провести `ЗаказПоставщику` (2 строки услуг) | `СтатусыПодтверждений`: ровно 2 записи (заказ, услуга), статус `Отправлен`, дата подтверждения пуста | | |
| A2 | Отменить проведение A1 | обе записи регистра удалены, документ не проведён | | |
| A3 | Провести `ПодтверждениеУслуги` только по одной услуге заказа | `СтатусыПодтверждений`: у первой строки `Подтверждён` + дата документа, у второй остаётся `Отправлен`; `ПараметрыУслуг` записаны; заявка **не** подтверждена (частично) | | |
| A4 | Провести подтверждение второй услуги | статус заявки `Подтверждена`; оборот `KPIОператоров.ОбработанаЗаявка`; время оборота = дата документа (детерминизм, см. design D5) | | |
| A5 | Отменить проведение A4 | статус заявки откатился (`ВРаботе`), KPI-оборот удалён, запись `СтатусыПодтверждений` вернулась к `Отправлен` | | |
| A6 | Провести `МаршрутныйЛист` со всеми событиями | `ГрафикПеремещений`: по записи на событие с измерениями (м/лист, событие, турист, объект, тип), времена UTC | | |
| A7 | Провести тот же м/лист повторно без изменений | число записей регистра не изменилось (нет дублей) | | |
| A8 | `КорректировкаМаршрута` без `Согласовано=Истина`, попытка записи | запись отклонена с текстом о необходимости согласования | | |
| A9 | То же с согласованием: изменить время одного события, провести | в `ГрафикПеремещений` новые времена; локальное время и буферы в м/листе пересчитаны | | |
| A10 | Отменить проведение A9 | прежние времена восстановлены, буферы откатаны | | |
| A11 | Провести `Инцидент` | `СтатусыИнцидентов`: одна запись `Открыт` с ответственным; реквизит `Статус` документа `Открыт` | | |
| A12 | Провести `ЗаявкаТуристаНаМаршруте` критичного типа | `ИсторияОбработокЗапросов`: действие `Регистрация`; создана задача руководителю (`ЗадачаИсполнителя`) | | |
| A13 | Провести `ПретензияПоставщику` (сумма ≤ порога) | оборот `ВзаиморасчётыПоПретензиям.СуммаТребования`; проведения нет, если поставщик/договор не соответствуют инциденту — проверить негатив: система отказывает с причиной | | |
| A14 | Претензия выше константы `ПорогСогласованияРуководителем` без флага согласования | запись/проведение отклонено с явным текстом о согласовании руководителем | | |
| A15 | Провести `АктОКомпенсации` по A13 | оборот `СуммаУдовлетворения`, записи `ШтрафыИКомпенсации` пропорциональны строкам, сумма строк = итог; инцидент → `Урегулирован` | | |
| A16 | Отменить проведение A15 | инцидент → `ВРаботе`, обороты сняты во всех трёх РН | | |

## B. Обработка ошибок: «не падает, а объясняет»

### B-I. Неверные данные (интерактивно)

Для каждого случая: заполнять нарушение и нажимать «Записать». Критерий: в журнале сообщений — текст с названием реквизита, сутью нарушения и требуемым действием (спека `data-validation`); записи в базе нет; новых дампов нет.

| № | Сценарий | Ожидаемый результат | Факт | Вердикт |
|---|---|---|---|---|
| B1 | `ДоговорыСПоставщиками`: `ДатаОкончания` < `ДатаНачала` | отказ, сообщение именует оба поля и правило | | |
| B2 | `Инцидент`: `ДатаИнцидента` в будущем | отказ, сообщение ссылается на текущую дату | | |
| B3 | `ЗаявкаТуристаНаМаршруте`: `СрокSLA` в прошлом | отказ с указанием, что срок уже истёк | | |
| B4 | `ЗаказПоставщику`: `ДатаОжиданияПодтверждения` позже минимальной `ДатаНачала` услуг | отказ, поле именовано | | |
| B5 | `ПроцентШтрафа` = 150 и −5; `МаксимальнаяКомпенсация` < 0; `SLAЧасов` = 0 | отказ по каждому, все нарушения за один проход (не по одному за попытку) | | |

### B-II. Отрицательные количества/суммы

| № | Сценарий | Ожидаемый результат | Факт | Вердикт |
|---|---|---|---|---|
| B6 | `ЗаказПоставщику`: строка услуг `Количество` = 0 и −1 | отказ, сообщение указывает строку ТЧ | | |
| B7 | `АктОКомпенсации`: сумма строки отрицательна; итог ≠ сумме строк | отказ по обоим правилам, поле именовано | | |
| B8 | `ПретензияПоставщику`: `СуммаВзысканияСПоставщика` > `СуммаТребования` | отказ | | |
| B9 | Негативы B6–B8 проверить повторной записью после исправления | запись проходит, прежние отказы не блокируют объект навсегда | | |

### B-III. Дубли ключей

| № | Сценарий | Ожидаемый результат | Факт | Вердикт |
|---|---|---|---|---|
| B10 | Загрузить `ОбменСФайлами` CSV номенклатуры, затем тот же файл второй раз | вторая загрузка: строки отклонены как дубли с указанием значения ключа и номера строки; число элементов не изменилось; вердикт отчёта «отклонено» | | |
| B11 | CSV со строкой-дублем внутри одного файла + одна строка с неразрешимой ссылкой | частично: валидные загружены, дубль и битая — в отчёте с причинами (спека `data-exchange`) | | |
| B12 | Справочник: элемент с существующим кодом/наименованием через форму | отказ или предупреждение о неуникальности (зафиксировать фактическое поведение как дефект, если запись проходит молча) | | |
| B13 | Повторное проведение после правки данных A6 | движения заменены, без удвоений (уже по A7 — здесь с изменённым содержимым) | | |

### B-IV. Отказ доступа (по ролям)

Ручная часть; автоматические эквиваленты — батарея `ПроверкаДоступа` (режимы `CHECK`/`CHECK+DATA`, см. `docs\Регрессия-прав.md`), но сообщения и поведение UI проверяются глазами.

| № | Учётка | Сценарий | Ожидаемый результат | Факт | Вердикт |
|---|---|---|---|---|---|
| B14 | `ТурГид` | Раздел «Заказы поставщикам» | команда создания недоступна (скрыта/запрещена), без ошибок платформы | | |
| B15 | `ТурГид` | Кнопка «Сформировать запросы поставщикам» (если видна) | сообщение «Недостаточно прав для …», отчёта нет, сеанс жив | | |
| B16 | `Аудитор` | Открыть документ из списка → попытка изменить и записать | форма только для чтения / запись отклонена платформой с внятным текстом | | |
| B17 | `Аудитор` | Запустить `ПересчётТайминговМаршрутов` | остановка на проверке прав с сообщением | | |
| B18 | `ОператорСопровождения` | Запустить `ПересчётТайминговМаршрутов` (право «Изменение» на `СобытиеМаршрута` отсутствует) | «Недостаточно прав…», не исключение | | |
| B19 | любая профильная | Попытка записи в регистр/объект вне прав платформы | отказ платформы **с** контекстом (что и почему нельзя) — «голый» текст платформы без объяснения помечать дефектом сообщения | | |
| B20 | учётка без `ТестоваяИнфраструктура` (создать временную) | Открыть внешнюю обработку `build\ПроверкаДоступа.epf` | платформа отказывает в интерактивном открытии; временную учётку удалить после проверки | | |

### B-V. Общие критерии раздела B

После каждого блока (B-I…B-IV): проверить отсутствие новых `Ошибка_*.zip` (LastWriteTime позже начала сессии) и зависаний; любой случай с дампом = FAIL чекпойнта + дефект высшего приоритета.

## C. Файловый режим и лимиты

| № | Сценарий | Ожидаемый результат | Факт | Вердикт |
|---|---|---|---|---|
| C1 | Свойства файла `db\КурсоваяРабота\1Cv8.1CD` + прогон `epf\ПроверкаДанных` | размер ≤ 2048 МБ, вердикт проверки содержит размер и признак запаса; сбоя нет | | |
| C2 | CSV: строка с наименованием 1500 символов | строка отклонена с указанием номера, причины «длина строки» и лимита 1024; остальные строки загружены | | |
| C3 | Первый сеанс держит открытую форму документа; запустить второй сеанс к той же файловой ИБ | явный отказ/предупреждение о занятой базе (или штатное поведение платформы для файловых ИБ, зафиксировать дословно); первый сеанс работает | | |
| C4 | `epf\ТестПроведения`: пакетное проведение всех документов набора | отчёт по каждому документу (проведён/отклонён/причина); зависаний нет; завершено за конечное время | | |
| C5 | `СводкаСтатусов` на базе после C4 и на расширенном наборе (кратность x10, задача 4.1 изменения) | отчёт сформирован, памяти/времени хватило, ошибок платформы нет | | |
| C6 | Повторный прогон `epf\ЗаполнениеНСИ` поверх наполненной базы | идемпотентность: удвоения объектов нет (сверка количеств до/после через `ПроверкаДанных`) | | |
| C7 | Восстановление из `.dt`-бэкапа после объёмных прогонов | база возвращается к демонстрационному набору, цепочка A1–A7 на ней проходит снова | | |

## D. Журнал дефектов

| № | Чекпойнт | Симптом | Класс (движения/ошибка/права/файловый) | Статус |
|---|---|---|---|---|
| | | | | |

Классификация: `крит` (сбой/дамп/потеря данных), `сущ` (неверное движение/статус/дубль), `сообщение` (правильный отказ, невнятный текст), `косметика`. Дефекты классов «сущ» и выше обязаны иметь запись в `openspec/changes/debug-and-stabilize` (фикс входит в задачи 2.5/3.4) или явное отложение с решением заказчика.

## E. Критерий готовности раздела

План считается выполненным, когда: все чекпойнты A–C имеют вердикт; нет открытых дефектов классов `крит`/`сущ`; каждый `сообщение`-дефект либо исправлен, либо отложен решением заказчика; итоговый отчёт прогона сохранён в `docs\` (задача 5.1).
