# Регрессия прав — как повторно прогнать батарею проверок

Дата: 2026-10-26. Источник: изменение `add-access-roles` (capability `access-roles`), отчёты задач 12–13 в `.superpowers/sdd/2026-10-23-add-access-roles-tasks-3.1-5.1/`.

Документ описывает, как после любых правок ролей, матрицы прав или harness-кода заново проверить ролевую модель: конвейер «матрица → роли → harness», подготовку базы, точный запуск, режимы EPF, сценарии и разбор доказательств.

## 1. Обзор: конвейер матрица → роли → harness

1. **`openspec/changes/add-access-roles/roles-matrix.json`** — единственный источник правды: матрица «роль × объект метаданных × право».
2. **`check-matrix.py`** (там же) — контроль матрицы: состав ролей/объектов, допустимые имена прав, согласованность со спекой. Запускается до генерации.
3. **`regenerate-roles.py`** — генерирует JSON ролей из матрицы: `openspec/changes/add-access-roles/roles/*.json` (6 профилей) и `roles-harness/ТестоваяИнфраструктура.json`. Вспомогательные: `emit-role-json.py`, `rights_map.py`, `restore-role-uuids.py` + `role-uuids.snapshot.json` (UUID существующих ролей обязаны сохраняться — особенно `Администратор`, `527785c9-…`).
4. **Скилл `role-compile`** — JSON → `src/КурсоваяРабота/Roles/<Имя>.xml` + `Ext/Rights.xml`; затем `role-validate` и `cf-validate`.
5. **Загрузка в ИБ** — скиллы `db-load-xml` (`LoadConfigFromFiles`) + `db-update` (`UpdateDBCfg`); команды к базе Designer — с `-UserName "Администратор"` (пароль пустой).
6. **Harness** — внешняя обработка `epf/ПроверкаДоступа` (исходники формы), сборка скиллом `epf-build` в `build/ПроверкаДоступа.epf`. Запускается под каждой учёткой и пишет лог-доказательство; сценарии — раздел 5.

Правило: перед каждой пересборкой EPF прогнать `1c-lsp-diagnostics` по `epf/ПроверкаДоступа/Forms/Форма/Ext/Form/Module.bsl` и убедиться, что `severity = 1` находок нет (AGENTS.md, п. 8).

## 2. Подготовка

- **Пользователи ИБ**: список пользователей базы содержит `Администратор` и 6 тестовых учёток профилей: `ОператорСопровождения`, `КоординаторЛогистики`, `ТурГид`, `МенеджерПоПретензиям`, `РуководительНаправления`, `Аудитор`. Аутентификация ИБ включена, **пароли пустые у всех**.
- **Назначение ролей**: каждой тестовой учётке — её `Профиль_*` **плюс** `ТестоваяИнфраструктура` (без неё учётка не может открыть внешнюю обработку в файловой ИБ); `Администратор` — роль `Администратор`. Если назначение сбилось — режимы `LIST`/`FIX` (раздел 4). Связь учётка ↔ `Справочник.Сотрудники` проверяется сценарием S6.
- **«Защита от опасных действий» снята** у всех тестовых пользователей. Грабля: это **не** отключает безопасный режим для EPF-сеансов профильных пользователей — файловая запись из EPF для них запрещена, поэтому лог таких сеансов снимается с `/Out` (нормализация, раздел 6).
- **Рабочий стол разблокирован**: запуск кликает диалоги через watchdog (раздел 3); на заблокированном desktop сеанс повиснет.
- **Лицензия на 1 место**: перед каждым запуском закрыть все сеансы 1С, `Get-Process 1cv8*` должен быть пуст. Прогоны строго последовательные, никогда не параллельные.
- `build/ПроверкаДоступа.epf` пересобран из актуальных исходников (`epf-build`, CheckConfig зелёный).

## 3. Запуск

Точная командная строка (проверенный launcher — `epf\run-epf2.ps1`, в репозитории; параметры — в `/C`):

```
"C:\Program Files (x86)\1cv8\8.3.27.1786\bin\1cv8c.exe" /F "db\КурсоваяРабота" /N "<логин>" /P "" /L 20 /Execute "build\ПроверкаДоступа.epf" /C "<параметры режима>" /Out "<evidence>\<префикс>-<логин>.out.log" /Exit
```

- **`/N "<логин>" /P ""` — обязательная пара.** Без `/P ""` платформа показывает окно входа и сеанс висит до timeout. Перед каждым запуском ассерт: логин непустой.
- **`/Out`** — файл лога платформы; для safe-mode пользователей это и есть доказательство (копируется в `<префикс>-<логин>.log`, пометка NORMALIZED).
- **Watchdog**: фоновый job, который гасит только лицензионный диалог `^1[СC]:Предприятие$` и кликает только кнопки OK/ОК/Да/Yes — **никогда «Войти»**. Если появилось окно входа — значит сломан `/N`/`/P ""`, watchdog его не трогает, прогон падает по timeout (так и задумано).
- **Timeout** ~240 с на запуск; нормальный прогон — около 3 с. Между запусками и в конце — `Get-Process 1cv8*` = 0, новых дампов нет.
- **Протокол краш-дампов** (AGENTS.md, п. 7): при TIMEOUT/ зависании — найти новейший `Ошибка_*.zip` в корне проекта (по `LastWriteTime`), распаковать, читать `report.json` → `errorInfo.applicationErrorInfo.errors`. Дамп свежее ~10 минут — это и есть причина; не повторять запуск, не устранив её. Отсутствие дампа успех не доказывает.
- **Параметры `/C`**: `Параметры[0]` — режим; для CHECK с данными `Параметры[3] = "DATA"`, `Параметры[4]` — маркер скретч-документов (по нему же cleanup собирает сирот). Авторитетный комментарий — заголовок `Module.bsl` (строки ~77–82).

## 4. Режимы EPF `ПроверкаДоступа`

| Режим | Кто запускает | Что делает / что пишет в лог |
|---|---|---|
| `CHECK` | каждый профильный пользователь, `Администратор` | Права по матрице (`ПравоДоступа`) + сценарии S1, S4–S9; строки-вердикты `expected=…|actual=…|PASS/SKIP/INFO`; провал — строка, содержащая `|FAIL` (итоговый маркер `FAILCOUNT` harness не пишет — в `Module.bsl` его нет) |
| `CHECK` + `DATA` (`Параметры[3]="DATA"`, `Параметры[4]=<маркер>`) | профильный пользователь | То же + скретч-данные S2/S3: создаёт документы с маркером, проверяет запись/проведение, пишет строки `MANIFEST: …` и `DATA|…` |
| `PROBE` | любой (диагностика) | Точечная проба прав/состояния сеанса — отладка зависаний и «молчащих» отказов |
| `FIX` | `Администратор` | Переназначает роли тестовым пользователям по эталонному списку (лечит сбившееся назначение) |
| `LIST` | `Администратор` | Перечисляет пользователей ИБ + их роли в лог (сверка назначения перед батареей) |
| `REG` | каждый профильный + `Администратор` | Регрессия соседних спек R1–R5 (раздел 5); R4 пишет/восстанавливает проведение демо-документа |

## 5. Сценарии

### S0–S9 (батарея прав, `CHECK`/`CHECK+DATA`)

| № | Пользователь | Проверяется |
|---|---|---|
| S0 | все 6 | Сеанс стартовал, строка логина `expected=<логин>|actual=<логин>` (expected=actual), лог непустой, нет строк `\|FAIL` |
| S1 | каждый профильный | Видимость подсистем: свои верхние + вложенные видны, чужие бизнес-разделы скрыты; `Аудитор` — 5 бизнес-подсистем да, `АдминистраторИС` нет. Логин вне матрицы S1 (`Администратор`) — строка `SKIP`, не FAIL |
| S2 | `ТурГид` | DATA: `Инцидент` создаётся и сохраняется **непроведённым**; `ДоговорыСПоставщики`/`ПретензияПоставщику` — нет Чтение/Просмотр |
| S3 | `ОператорСопровождения` | DATA: `ПодтверждениеУслуги` создаётся и **проводится**; `Туристы` ИнтерактивноеДобавление = Истина |
| S4 | `ОператорСопровождения` | Нет прав на `ПретензияПоставщику`; нет Просмотр `НастройкиИнтеграций`; нет Использование `ОбменСФайлами` |
| S5 | `Аудитор` / `КоординаторЛогистики` | `СтраныМира` только чтение; `ШтрафыИКомпенсации` Чтение; `ПересчётТайминговМаршрутов` Использование: Аудитор — нет, Координатор — да |
| S6 | `Администратор` (LIST/FIX) | Привязка учётка↔сотрудник: `ИмяПользователяИБ` точно + `Сотрудник` непустой ×2 |
| S7 | `МенеджерПоПретензиям` / `ОператорСопровождения` | `ВзаиморасчётыПоПретензиям` Чтение: да / нет |
| S8 | все 6 | Константа `ПорогСогласованияРуководителем` Чтение = Истина; перечисления — INFO «N/A by platform» |
| S9 | все 6 | `СохранениеДанныхПользователя` = Истина (тонкий клиент), право `ТонкийКлиент` |

Cleanup после DATA-прогонов: проход A (админ) удаляет сирот по маркеру из `MANIFEST`-строк, проход B проверяет «0 сирот, манифест пуст» (`…-cleanupA.log` / `…-cleanupB.log`).

### R1–R5 (регрессия соседних спек, `REG`)

| № | Спека | Проверяется |
|---|---|---|
| R0 | — | В каждом REG-логе: логин сеанса = ожидаемый (страховка от класса «окно входа») |
| R1 | `navigation-and-commands` | Точечные `ПравоДоступа` по профилям: Просмотр/ИнтерактивноеДобавление/ИнтерактивноеПроведение/Редактирование/Чтение документов и справочников (~20 проверок) |
| R2 | `data-processors` | Матрица Использование 5 обработок × 6 профилей = 30 ячеек против п. 6 спеки `access-roles`; `ОбменСФайлами` — нет у всех шести |
| R3 | `data-exchange` | Админ: экспорт `ВыгрузитьНоменклатуру` → временный CSV (файл создан, непустой, заголовок и verdict=PASS); Оператор: нет Использование `ОбменСФайлами`. Импорт-ветка не выполняется (защита демо-данных) |
| R4 | `document-posting` | Админ: round-trip проведение демо-`ПодтверждениеУслуги` (первый по Дата/Номер, скретч исключены) и **восстановление состояния**: строки before/after равны (net-zero) |
| R5 | админ-smoke | Использование `СводкаСтатусов`/`ПросроченныеСрокиИSLA` + немодальное открытие/закрытие обеих форм headless, без исключений |

## 6. Где доказательства

- Каталог: `.superpowers/sdd/<каталог-изменения>/task-N-evidence/` (для `add-access-roles` — `task-12-evidence/`, `task-13-evidence/` в `.superpowers/sdd/2026-10-23-add-access-roles-tasks-3.1-5.1/`).
- Именование: `<префикс>-<логин>.log` — нормализованный лог сценария (`final-` первая батарея, `rerun-` перезапуск после фикса, `reg-` REG-режим, `check-`/`probe-`/`diag-` разовые прогоны); `<…>.out.log` — сырой вывод `/Out`; `superseded-*` — устаревшие логи, заменённые перезапуском (не удалять, не использовать как доказательство); `scratch-manifest.txt`, `*-cleanupA/B.log`, `R3-nomenklatura-export.csv` — артефакты DATA/REG.
- Для safe-mode пользователей (все профильные) платформенный лог пуст — runner копирует `/Out` в основной `.log` и печатает NORMALIZED; содержимое доказательств идентично.
- Критерий зелёного прогона: у всех запусков `exit=0`, логи непустые, в логах **нет ни одной строки, содержащей `|FAIL`**, каждая строка-вердикт заканчивается на `PASS`/`SKIP`/`INFO`, в строке S0 `expected=actual=<логин>`, cleanup-проход B — 0 сирот, `newDumps=[]`, `1cv8*` процессов 0. (Ранее здесь фигурировал итоговый маркер `FAILCOUNT` — harness его никогда не выводил; исторические логи не переписываем.)

## 7. Восстановление после правки матрицы

1. Отредактировать `openspec/changes/add-access-roles/roles-matrix.json`.
2. `python check-matrix.py` — матрица валидна (состав, имена прав, объекты существуют в метаданных).
3. `python regenerate-roles.py` — перегенерировать JSON ролей; UUID восстановятся из `role-uuids.snapshot.json` (`restore-role-uuids.py`) — проверить, что UUID `Администратор` и существующих профилей не изменились.
4. `role-compile` по каждому изменённому JSON → XML в `src/КурсоваяРабота/Roles/`; `role-validate` + `cf-validate` зелёные.
5. `db-load-xml` + `db-update` (сеансы 1С закрыты; Designer с `-UserName "Администратор"`); после — нет новых `Ошибка_*.zip`.
6. Если правили модуль harness: `1c-lsp-diagnostics` (sev1 = 0) → `epf-build` → canary-прогон под `Администратор` (CHECK, ~3 с, exit 0) перед батареей.
7. Батарея: CHECK+DATA под 6 профилями → cleanup A/B → REG под 6 профилями + `Администратор`. Во всех логах нет строк `|FAIL` (критерий раздела 6), доказательства — в новый каталог `task-N-evidence/` по конвенции раздела 6.

## 8. Грабли harness-кода (проверено на практике)

- **Append к тексту с тонкого клиента**: `Новый ЗаписьТекста(путь, UTF8, Истина)` из `&НаСервере` вызова тонкого клиента **обрезает** файл и пишет «Да» вместо переводов строк. Дозапись — только read-then-full-rewrite (процедура `ЗаписатьЛог`).
- **Форматирование булева**: `"БИ=Истина;БЛ=Ложь"`. Строка `"БЛ=Истина;БЛ=Ложь"` задаёт представление Ложь дважды и молча искажает доказательство (вердикты считаются по сырому Булево — но логи станут врать).
- **Скретч-документы**: перед записью обязательно `ДокументОбъект.Дата = ТекущаяДатаСеанса()`, иначе «Значение поля "Дата" не может быть пустой датой».
- **Файловая запись из EPF**: у профильных пользователей запрещён безопасный режим независимо от флага «Защита от опасных действий» — любой код harness обязан работать без файлового I/O на клиенте (лог через `Сообщить`/`/Out`, манифест через строки лога).
- **Модальные ошибки = висяк**: весь клиентский `ПриОткрытии` — в `Попытка/Исключение`, `ЗавершитьРаботуСистемы` выполняется безусловно.
