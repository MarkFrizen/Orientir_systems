## 1. Проведение девяти документов

**Что сделано.** У каждого документа появились `ОбработкаПроведения` и `ОбработкаУдаленияПроведения`: проведение формирует движения и меняет статусы, отмена снимает движения и возвращает статусы, повторное проведение не создаёт дублей.

**Где в исходниках:**

```
src/КурсоваяРабота/Documents/<Имя>/Ext/ObjectModule.bsl
```

процедуры `ОбработкаПроведения` и `ОбработкаУдаленияПроведения` в области «ОбработчикиСобытий».

**Где в Конфигураторе:** Документы → `<Имя>` → Действия → Открыть модуль объекта.

**Как проверить:** раздел → подсистема → журнал → открыть документ → «Провести». Движения — в Конфигураторе: Регистры сведений или Регистры накопления → нужный регистр → Открыть → отбор по «Регистратор».

**Автоматическая проверка:** сценарии `post-*` тестового набора (раздел 7).

## 2. Движения по матрице «Документ → Регистр → Тип движения»

| Документ | Регистр или объект | Что записывается |
|---|---|---|
| `ЗаказПоставщику` | РС `СтатусыПодтверждений` | статус `Отправлен`, пустая дата подтверждения — по строке на услугу |
| `ПодтверждениеУслуги` | РС `СтатусыПодтверждений`, РС `ПараметрыУслуг`, РН `KPIОператоров` | статус `Подтверждён` с датой; фактические параметры услуги; KPI `ОбработанаЗаявка` |
| `ПодтверждениеУслуги` | `Справочник.ЗаявкиНаТур` | при полном подтверждении — статус `Подтверждена` |
| `МаршрутныйЛист` | РС `ГрафикПеремещений` | событие, турист, объект, тип события, времена UTC, длительность |
| `КорректировкаМаршрута` | РС `ГрафикПеремещений` | замена времён событий, пересчёт `ЛокальноеВремя` и `БуферДоСледующегоМинут` |
| `СобытиеМаршрута` | — | движений нет: события попадают в график через маршрутный лист |
| `ЗаявкаТуристаНаМаршруте` | РС `ИсторияОбработокЗапросов` | действие `Регистрация` с инициатором; при критическом типе — задача руководителю |
| `Инцидент` | РС `СтатусыИнцидентов` | статус `Открыт` с ответственным |
| `ПретензияПоставщику` | РН `ВзаиморасчётыПоПретензиям` | `СуммаТребования` |
| `АктОКомпенсации` | РН `ВзаиморасчётыПоПретензиям`, РН `ШтрафыИКомпенсации`, РН `KPIОператоров` | сумма удовлетворения; компенсации по видам; KPI `УрегулированИнцидент` |
| `АктОКомпенсации` | `Справочник.Инциденты` (статус) | инцидент переводится в `Урегулирован` |

**Как убедиться:** Конфигуратор → Регистры → выбрать регистр → Открыть → колонка «Регистратор» покажет документ-источник. Для `СтатусыПодтверждений` и `ПараметрыУслуг` отбор ставится по «Регистратор»: набор записей подчинённого регистра фильтруется только регистратором.

### Как пишутся движения

Движения записываются **только через коллекцию `Движения`** документа:

```
Движение = Движения.СтатусыПодтверждений.Добавить();
...
Движения.СтатусыПодтверждений.Записать();
```

Через менеджер регистра (`РегистрыСведений.X.СоздатьНаборЗаписей()` + `Записать(Истина)`) писать нельзя. При `ЗаписьДвиженийПриПроведении = Записывать выбранные` платформа в конце проведения записывает коллекцию `Движения` и затирает всё, что записано мимо неё. Коллекция инициализирована только при записи из открытой формы документа — поэтому такой код работает из журнала, из внешней обработки и через COM, но **молча не пишет ничего при проведении из формы**: документ проведён, ошибок нет, движений нет.

Прежние движения при повторном проведении снимает платформа (автоудаление движений при проведении), вручную их удалять не нужно.

Исключение — `КорректировкаМаршрута`: она правит записи графика, зарегистрированные **маршрутным листом**, поэтому читает и записывает набор по отбору `Регистратор = МаршрутныйЛист`. Коллекция `Движения` корректировки к этим записям отношения не имеет.

## 3. Общие модули

### `ПроведениеДокументов`

Единственная процедура `ЗаблокироватьРегистры(МассивРегистров)` — ставит исключительную блокировку по областям.

Режим именно исключительный: разделяемая блокировка с последующей записью в тот же регистр в файловой базе не завершается — транзакция ожидает повышения собственной блокировки, сообщения об ошибке нет, дампа тоже.

**Где:** `src/КурсоваяРабота/CommonModules/ПроведениеДокументов/Ext/Module.bsl`, свойства модуля — `CommonModules/ПроведениеДокументов.xml`.

### `ЗадачиИсполнителям`

`СоздатьЗадачу(Наименование, Описание, Исполнитель, ОбъектОснования)` и `ЗакрытьЗадачу(ЗадачаСсылка, Комментарий)`.

Адресация задач идёт через регистр сведений `АдресацияЗадач` с единственным измерением `Исполнитель`; модуль создаёт в нём маркер исполнителя, иначе задача не попадает в список адресованных.

**Где:** `src/КурсоваяРабота/CommonModules/ЗадачиИсполнителям/`.

**Проверка:** сценарий `task-addressing`.

## 4. Четыре обработки

| Обработка | Где в Конфигураторе | Где в интерфейсе ИБ | Что делает |
|---|---|---|---|
| `ФормированиеЗапросовПоставщикам` | Обработки → модуль объекта | Оператор сопровождения → Заказы поставщикам | создаёт заказы по заявкам, у которых ещё нет услуг в заказах; повторный запуск даёт «пропущено» |
| `ПересчётТайминговМаршрутов` | Обработки | Координатор логистики → Корректировки | пересчитывает локальное время и буферы, собирает накладки; проведённые документы меняет только по флагу |
| `ПросроченныеСрокиИСЛА` | Обработки | Руководитель направления → Эскалации | ищет просроченные контрольные сроки и SLA, по флагу создаёт задачи эскалации |
| `СводкаСтатусов` | Обработки | Руководитель направления → Отчёты KPI | сводка по статусам заявок, подтверждений, инцидентов и претензий, выгрузка в CSV |

В модуле `СводкаСтатусов` дополнительно реализованы запросы `СальдоПоПретензии(ПретензияСсылка)` (сальдо по движениям регистра) и `KPIСотрудников(Период, Сотрудник)`, а также `ВыгрузитьВФайл`.

**Где в исходниках:** `src/КурсоваяРабота/DataProcessors/<Имя>/`.

**Привязка к разделам:**

```
ОператорСопровождения   -> ЗаказыПоставщикам -> ФормированиеЗапросовПоставщикам
КоординаторЛогистики    -> Корректировки     -> ПересчётТайминговМаршрутов
РуководительНаправления -> Эскалации         -> ПросроченныеСрокиИСЛА
РуководительНаправления -> KPIОтчеты         -> СводкаСтатусов
```

**Где посмотреть состав подсистемы:** `src/КурсоваяРабота/Subsystems/<Раздел>/Subsystems/<Подсистема>.xml`, внутри `<Content>` строки вида `<xr:Item xsi:type="xr:MDObjectRef">DataProcessor.<Имя></xr:Item>`.

## 5. Проверки прав в обработках

Каждая обработка в начале `ВыполнитьОбработку` проверяет право и отказывает исключением, не раскрывая состав данных:

| Обработка | Право и объект |
|---|---|
| `ФормированиеЗапросовПоставщикам` | `ПравоДоступа("Добавление", Метаданные.Документы.ЗаказПоставщику)` |
| `ПересчётТайминговМаршрутов` | `ПравоДоступа("Изменение", Метаданные.Документы.СобытиеМаршрута)` |
| `ПросроченныеСрокиИСЛА` (с задачами) | `ПравоДоступа("Добавление", Метаданные.Задачи.ЗадачаИсполнителя)` |
| `ПросроченныеСрокиИСЛА` (без задач) | `ПравоДоступа("Просмотр", Метаданные.Документы.ЗаявкаТуристаНаМаршруте)` |
| `СводкаСтатусов` | `ПравоДоступа("Просмотр", Метаданные.Справочники.ЗаявкиНаТур)` |

**Где смотреть:** первые строки процедуры `ВыполнитьОбработку` в модуле объекта каждой обработки.

**Ограничение.** Отрицательная ветка (отказ при отсутствии права) исполнением не проверена: в базе один пользователь с ролью `Администратор`, а роль выдаёт все права по умолчанию (`setForNewObjects=true`). Проверка переносится на момент появления профилей групп доступа.

| `РегистрНакопления.KPIОператоров` | список регистра скрыт в командном интерфейсе | KPI нельзя ввести вручную, только проведением |

**Где смотреть:** `src/КурсоваяРабота/Documents/МаршрутныйЛист.xml` (блок `RegisterRecords`), `Documents/КорректировкаМаршрута.xml` (табличная часть `Изменения`), `Ext/ClientApplicationInterface.xml`.

### Почему KPI считается только автоматически

Регистр `KPIОператоров` — оборотный и подчинён регистратору. Записи в нём может создавать только проведение документа; список регистра скрыт из интерфейса. Обороты формируются при проведении `ПодтверждениеУслуги` (вид операции `ОбработанаЗаявка`) и `АктОКомпенсации` (вид операции `УрегулированИнцидент`). Универсальный помощник `ЗарегистрироватьKPI` из общего модуля удалён: он писал через менеджер записи, что для такого регистра недопустимо. Оборот пишется через `Движения.KPIОператоров` — как и остальные движения (см. раздел 2).

## 7. Тестовая обвязка

**Состав.** Внешняя обработка `epf/ТестПроведения` и PowerShell-раннер `tests/posting/run-posting-tests.ps1`. Двадцать один сценарий: девять `post-*`, `task-addressing`, четыре `proc-*`, `query-saldo`, `query-kpi`, `integrity`, `errors-dates`, `errors-amounts`, `verify-snapshot`, `selftest`.

**Где:** `epf/ТестПроведения/Forms/Форма/Ext/Form/Module.bsl` — сценарии; `tests/posting/run-posting-tests.ps1` — раннер; `build/ТестПроведения.epf` — сборка (в репозиторий не входит).

**Запуск:**

```
powershell -ExecutionPolicy Bypass -File tests\posting\run-posting-tests.ps1
```

**Где смотреть результат:** `%TEMP%\posting-tests\<сценарий>.txt` — построчные проверки и вердикт. Сводка печатается в консоль: `ИТОГО: 18/18`.

**Изоляция прогонов.** Перед прогоном и в `finally` после него выполняется сервисный сценарий `purge-test`: снимает проведение и физически удаляет тестовые объекты. Оборванный прогон не засоряет базу. Для разового разбора объектов, оставшихся от прежних версий сценариев, предусмотрен `purge-legacy`.

**Служебные сценарии диагностики:** `lock-probe` (проверка управляемых блокировок), `purge-probe` (проверка доступности физического удаления), `rights-probe` (перечень допустимых имён прав). В основной набор не входят.
